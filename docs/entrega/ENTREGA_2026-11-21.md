## 3. Lista previa a la entrega (acciones de la dueña del proyecto)

Estas acciones son manuales y no están hechas por esta nota.

1. **Desplegar `main` en Render.** `autoDeploy: false`: hay que hacer Manual Deploy de `sghu-api` y de `sghu-web`.
2. **Sincronizar `render.yaml` en Render.** La reescritura `/*` → `/index.html` y las cabeceras de seguridad (CSP, HSTS) no se aplican solas. Mientras no se sincronicen, producción da 404 en `/publico`, `/recuperar`, `/restablecer`, `/registro` y `/aceptar-invitacion`.
3. **Migraciones de la nube.** Todas hasta `20261116002000_fase1_contrato_api.sql` ya están aplicadas en producción. Falta `20261114000300_ticket_activo_unico.sql`, que se aplica pasada la medianoche local del 14-nov, a mano en el SQL Editor de Supabase (`docs/desarrollo/ges-15-supabase-remoto.md`). No uses `supabase db push`.
4. **Desactivar el inicio de sesión de prueba.** Si se fusiona el selector temporal de rol (`docs/operacion/login-de-prueba.md`), debe quedar apagado antes de la entrega: con él activo cualquiera elige un rol sin credenciales.
5. **Comprobar la API.** `GET https://sghu-api.onrender.com/salud` debe responder 200. El plan gratuito duerme tras 15 minutos: la primera llamada tarda cerca de un minuto. Si `GET /api/v1/publico/ocupacion` responde 404, Render sirve una versión anterior.
6. **URLs de Supabase Auth.** La web envía el correo de recuperación con redirección a `https://sghu-web.onrender.com/restablecer` (`web/src/App.tsx`); esa URL, y la de aceptar invitación, deben estar permitidas en Supabase Auth (ajuste del panel de Supabase).
7. **Cuentas.** Hay una cuenta de demostración por rol; las credenciales se entregan por un canal privado del equipo.
8. **Datos para la agenda.** El médico de prueba necesita una inscripción vigente y un turno publicado el día de la demostración (lo crea JOP en **Turnos**).
9. **APK firmado.** Para instalar un Release hace falta el keystore y las cuatro variables `CLIMESA_RELEASE_*` (`android/README.md`).
10. **iOS.** Antes de la defensa, probar en un simulador o iPhone con una cuenta MED y otra PAC (cada pantalla de la tabla de `ios/README.md`). Sin cuenta de Apple no hay IPA.

## 4. Antes de probar

- Después de cada despliegue usa `Ctrl + F5` en la web.

### Generar e instalar el APK (Windows)

Requisitos: Android Studio o Android SDK 35, JDK 17 y un teléfono con depuración USB autorizada.

```powershell
cd android
$androidSdk = "$env:LOCALAPPDATA\Android\Sdk"
"sdk.dir=$($androidSdk -replace '\\','/')" | Set-Content .\local.properties
```

Para que un **Debug** use la API de producción, agrega a `%USERPROFILE%\.gradle\gradle.properties`:

```properties
CLIMESA_API_BASE_URL=https://sghu-api.onrender.com/api/v1
```

Después:

```powershell
.\gradlew.bat clean testDebugUnitTest assembleDebug
adb devices
adb install -r .\app\build\outputs\apk\debug\app-debug.apk
adb shell monkey -p sv.edu.catolica.climesa 1
```

El teléfono debe aparecer como `device` en `adb devices`. `local.properties` y `gradle.properties` del usuario no se suben al repositorio. Para un build Release (`assembleRelease`) la URL de producción ya es la predeterminada. Con las cuatro variables `CLIMESA_RELEASE_*` el APK sale firmado (`app-release.apk`); sin ellas sale `app-release-unsigned.apk`, que no se instala (ver `android/README.md`, "APK release firmado").
