## 3. Antes de probar

1. **La producción puede no reflejar esta rama.** Render tiene `autoDeploy: false` (`render.yaml`): la web y la API se publican a mano. Antes de la defensa hay que desplegar la versión aprobada en `sghu-api` y `sghu-web`.
2. **Migraciones pendientes en la nube.** Esta rama agrega `20261114000100_diagnostico_principal.sql`, `20261114000200_integridad_citas_consulta.sql` y `20261114000300_ticket_activo_unico.sql`. Se aplican a mano en el SQL Editor de Supabase, en orden de fecha, siguiendo `docs/desarrollo/ges-15-supabase-remoto.md`. No uses `supabase db push`.
3. **Comprobar la API.** `GET https://sghu-api.onrender.com/salud` debe responder 200. El plan gratuito duerme tras 15 minutos sin tráfico: la primera llamada tarda cerca de un minuto. Si `GET /api/v1/consultas/agenda` responde 404, Render todavía sirve una versión anterior.
4. **Cuentas.** Hay una cuenta de demostración por rol. Las credenciales se entregan por un canal privado del equipo; no están en el repositorio.
5. **Datos para la agenda.** Para que haya citas, el médico de prueba necesita una inscripción vigente y un turno publicado en el día de la demostración (lo crea JOP en **Turnos**).

## 5. Cómo probar por rol (web de producción)

Abre https://sghu-web.onrender.com e ingresa con la cuenta de demostración del rol. Después de cada despliegue usa `Ctrl + F5`. El menú solo muestra los módulos para los que la cuenta tiene permiso.

| Rol | Módulos | Prueba sugerida | Resultado esperado |
|---|---|---|---|
| ADM | Usuarios, Personal, Edificio, Turnos | Invitar una cuenta ficticia y asignarle un rol | La cuenta aparece en Usuarios; el cambio queda en auditoría |
| JOP | Turnos, Personal, Camas, Edificio, Hospitalización, Inventario, Ambulancia | Asignar un turno al médico de prueba para hoy; volver a asignarlo en la misma jornada | La segunda asignación se rechaza (traslape o descanso) |
| JOP | Ambulancia | Poner la unidad en mantenimiento y sacarla | El estado cambia y las otras sesiones lo ven sin recargar |
| REC | Pacientes, Citas, Fila del día, Hospitalización, Camas | Buscar un paciente ficticio, confirmar una cita solicitada, emitir número de fila | La cita pasa a `Confirmada`; el número aparece en la fila |
| REC | Hospitalización | Crear admisión y asignar una cama sugerida | La cama queda ocupada en el tablero; una segunda asignación a la misma cama devuelve conflicto |
| MED | Mi consultorio | Iniciar consulta desde una cita confirmada, registrar signos y diagnóstico, emitir receta, pedir un examen y firmar | La cita pasa a `Atendida`; la consulta firmada ya no se edita; la orden aparece en Laboratorio |
| LAB | Laboratorio | Tomar muestra (doble identificación), capturar resultados y completar | La orden pasa `Pendiente → En Proceso → Completado`; una identificación que no coincide se rechaza |
| MED | Laboratorio / Mi consultorio | Revisar el resultado completado | El paciente puede ver los valores solo después de esta revisión |
| DPD | Usuarios, Auditoría | Abrir Auditoría | Se ven metadatos (quién, cuándo, qué) sin contenido clínico |

### Generar e instalar el APK (Windows)

Requisitos: Android Studio o Android SDK 35, JDK 17 y un teléfono con depuración USB autorizada.

```powershell
cd android
$androidSdk = "$env:LOCALAPPDATA\Android\Sdk"
"sdk.dir=$($androidSdk -replace '\\','/')" | Set-Content .\local.properties
```

Para que un **Debug** use la API de producción, agrega a `%USERPROFILE%\.gradle\gradle.properties`:

```properties
CLIMESA_API_BASE_URL=https://sghu-api.onrender.com/api/v1
```

Después:

```powershell
.\gradlew.bat clean testDebugUnitTest assembleDebug
adb devices
adb install -r .\app\build\outputs\apk\debug\app-debug.apk
adb shell monkey -p sv.edu.catolica.climesa 1
```

El teléfono debe aparecer como `device` en `adb devices`. `local.properties` y `gradle.properties` del usuario no se suben al repositorio. Para un build Release (`assembleRelease`) la URL de producción ya es la predeterminada, pero se necesita configurar la firma.
