# Navegación Android y tablero Web profesional
Objetivo: cerrar 121-T02 y 113-T01-WEB con una experiencia visual profesional, atractiva, clara y accesible. Rama: `SCRUM-102-hu-121-1`; entrega por plataforma antes de cualquier PR.
Estrategia: `ask-on-risk`; previsión 600–900 líneas; sin commit, push ni PR hasta autorización explícita. Verificación: Gradle Android, Vitest/build Web, progreso y prueba física/manual.

## Specs

1. **S1 — Continuidad autorizada.** El usuario pidió: “perfecto continua con todo eso master como recomiendas”. Alcance interpretado desde el paso inmediatamente anterior: completar `121-T02`, luego `113-T01-WEB`, sin incluir iOS.
2. **S2 — Calidad profesional multiplataforma.** El usuario pidió: “quiero un front end bastante profesional para android y web”. Debe reutilizar `docs/diseno/guia-diseno-web-android.md`, mantener textos de interfaz en español y evitar dependencias nuevas salvo necesidad demostrada.
3. **S3 — Identidad llamativa sin ruido.** El usuario pidió: “la UI debe ser llamativa para el user”. La capa astral se limita a identidad, jerarquía y orientación; no compite con datos, formularios, alertas ni privacidad.
4. **S4 — UX inequívoca.** El usuario pidió: “no debe de perderse en como funciona la UX”. Cada rol debe encontrar su destino principal, entender selección/estado/acción, volver atrás y reconocer carga, vacío, error, permiso y desconexión sin depender solo del color.
5. **S5 — Ocho roles Android.** El criterio vigente es JOP, REC, AST, ENF, MED, LAB, PAR y PAC. `121-T02` termina cuando el escenario 1 pasa para los 8 roles; JOP usa solo A26, A10 y A12 mientras no exista pantalla operativa propia en `pantallas.csv`; `ShiftPlanningScreen` no forma parte de la aceptación.
6. **S6 — Navegación Android adaptable.** Teléfono compacto usa barra inferior con 3–5 destinos prioritarios y “Más” cuando aplique; ancho medio/amplio usa rail o drawer. La rotación no pierde estado y los destinos se derivan de permisos efectivos de `/auth/me`.
7. **S7 — Tablero Web W03.** `113-T01-WEB` conserva privacidad agregada y debe cumplir: “el tablero se ve en la web desplegada para el avance, con conteos directos de camas, personal y pacientes (las vistas en vivo llegan en T02)”. Debe incluir ocupación por planta y huecos de cobertura cuando los contratos existentes los permitan, además de marcadores explícitos para la semana correspondiente.
8. **S8 — Navegación Web adaptable.** Web usa sidebar expandida, rail compacto y drawer móvil según ancho; foco, teclado, contraste, tema claro/oscuro y reducción de movimiento deben seguir la guía canónica.
9. **S9 — Verificación.** Android requiere pruebas unitarias, `testDebugUnitTest assembleDebug` y recorrido de los ocho roles en el Samsung S24 Ultra. Antes de cualquier prueba de nube se debe comprobar `https://sghu-api.onrender.com/salud` y continuar solo con `status: ok` y `database: ok`. Web requiere pruebas, build y validación manual del shell/tablero. Al cierre se ejecutan ambos comandos de progreso.
10. **S10 — Control humano de entrega.** No se crea commit, push ni PR sin una orden explícita del usuario; antes de entrega se separarán Android y Web en unidades revisables de una sola plataforma.
